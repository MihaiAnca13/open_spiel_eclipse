# Eclipse 4P RL — outstanding work

**Goal:** an Eclipse agent strong enough to play against competitively in 4-player games.

This file replaces three earlier research documents (`eclipse_rl_forward_ways.md`,
`docs/rl_scaling_report_2026-08-06.md`, `docs/eclipse_rl_architecture_report.md`), which were
generated by a fast/low-reasoning model and have been deleted. Two of their central conclusions
were wrong — see "Corrected diagnosis" below — and their priority ordering was wrong because none
of them checked whether the observation tensor contained the information needed to play Eclipse.
It did not. That was the binding constraint and it is now fixed.

Full history of the earlier sprints remains in `ppo_eclipse_plan.md`.

## Corrected diagnosis (keep this; it changes what is worth doing)

**There is no "degenerate mutual-casualty basin."** The `wipeout≈0.4 / vp_all≈4` figures those
reports built their thesis on are the *stochastically sampled training window* at
`ent_coef=0.05`. The same update's argmax eval (`runs/csoft_20260805162200.log:5269-5464`, update
18220 / 401.8M steps) reports `wipeout=0.00`, +0.602 vs Random and +0.699 vs Greedy (chance
+0.250), 32/32 wins. `runs/meta/monitor_log.md:22-24` had already caught this. So R-NaD, RND,
PBT and exploiter pressure — their top recommendations — target a problem the eval data
contradicts. Deprioritized.

**The frozen LR had a concrete cause.** `main()`'s `for update in range(num_updates)` restarts at
0 every launch and that loop counter, not `agent.updates_done`, drives
`anneal_learning_rate` (`ppo_eclipse.py:1872`, `:1994`). The log shows it: updates advance at
16,384 steps each yet the final line is `[update 18300]` at `steps=403095552`. So each resume
reset the LR to full base and re-annealed over a fresh 300M window. See Phase 0b.

**Throughput was never the bottleneck** the scaling report assumed — its case for
SampleFactory/EnvPool rested on superseded sync-env numbers.

Also worth keeping: **Eclipse models no per-player private state** (`InformationStateString`
just returns `ObservationString`, `eclipse.cc:1666-1670`), so play-time search needs no belief
modelling, determinization or IS-MCTS. And the **9-category VP breakdown is already computed
every step** (`scoring.cpp:107-155`) — it is now exposed, giving 9 free dense aux targets.

## DONE — observation tensor rewritten for total coverage

`open_spiel/games/eclipse/observation.{h,cpp}` is new and is the single source of truth.
`ObservationTensor` in `eclipse.cc` is now a thin call into it.

- **1,785 → 20,439 floats**, all values in [0,1], 79.8 KB per observation.
- **One identical block schema for all six seats** (547 floats each), seat-relative with slot 0
  always the viewer, replacing the fat-self-135 / thin-opponent-25 asymmetry. Every player id in
  the tensor (combat attacker, `ambassador_from`, upkeep player, …) is remapped to be
  viewer-relative, so the tensor is canonical.
- Newly visible per seat: resources, **true production** (`POPULATION_PRODUCTION_TABLE[idx]`, not
  the backwards raw index), income / upkeep cost / net cash / solvency **every step** (previously
  only while the upkeep sub-state ran), all 40 tech bits, all four blueprints with mounted parts,
  the full 5-slot reputation track, parts inventory, minor species, per-`BuildType` build costs,
  turn/pass order, and the 9-category VP breakdown.
- Newly visible per galaxy cell (69 channels): planet slots **printed and populated** by
  `PlanetType`, sector VP, **rotated** wormhole edges, ring kind, buildings, per-ship-type unit
  counts for self / enemy / NPC, damage, anchor, and combat/move/explore markers.
- **Combat in full** — initiative order, battle queue, the **dice actually rolled** and the units
  they may be assigned to, retreats, destroyed ships. Previously 15 of ~54 fields with every array
  omitted, so the agent fought battles blind to the order, the dice and the targets.
- **Explore's drawn tiles described feature-by-feature**, so rotate/place/discard is not blind.
- **Move's selected unit and steps remaining.**
- **Diplomacy, which previously had no representation at all** — including `ambassador_from`, so
  *who* a relation is with is finally readable.

**One deliberate exception to "expose everything":** `Sector.discovery_tile` is the identity of a
**face-down** tile (written at placement, `explore.cpp:472-477`; cleared only on claim). Exposing
it would be cheating and would make the agent unfair to play against. Only
`discovery_tile_present` is exposed, and `ObservationLayoutTest` flips the hidden identity and
asserts the tensor stays bit-identical.

Also done: the galaxy block now buckets the unit registry in **one pass** instead of the old
O(225 × |registry|) rescan-per-cell; `obs_layout.py` mirrors the layout with named offsets, a
`validate(game)` drift guard and `galaxy_view()` → `(69, 15, 15)`; `ppo_eclipse.py`'s stale
offsets are all removed and `phi_soft_self`/`phi_soft_opponent` collapsed into one
`phi_soft_block` (both shaping call sites lost their same-seat/different-seat branch entirely).

Tests: `eclipse_test` **80/80** green including the new `ObservationLayoutTest` (seat
canonicalization round-trip, wormhole rotation across all 6 rotations, printed-vs-populated
planets, discovery-tile secrecy). The writer self-checks its cursor against the named offsets.

### Measured throughput — the gate fired, and it points at the encoder

128 envs / 16 workers, same config as the 400M-step run:

| config | envstep/s |
|---|---|
| old 1,785-float obs, production arch (512/3, separate critic) | ~15,300 |
| new 20,439-float obs, **narrow** net (64/2, shared trunk) | **13,635** |
| new 20,439-float obs, production arch (512/3, separate critic) | **2,655** |

The 11.5× wider tensor costs only ~11% on its own. The 5.1× collapse is the **flat trunk**:
`Linear(20439, 512)` twice (separate critic) is ~21M params in the first layers, over a
16,384-row batch per update. `ObservationTensor` is 0.141 ms/call — 97% of raw engine
per-decision cost, but only ~1.1 ms/worker/step at 8 envs/worker, so not binding.

**Do not trim the tensor. Land the spatial encoder.** Until then, use a narrow shared trunk.
Rollout buffer at 128×128 is 1.34 GB (fine on 12 GB; fp16 storage is a later option).

### 4. Closed-loop LR and entropy control (needs 0b first)

### 6. Play-time search + the UI opponent (the deliverable)

Budget: a few seconds per AI move.

Facts established, correcting Sprint C's premise: `explore_draw`, `combat_roll` and
`reputation_draw` **are** real chance nodes with fully explicit `ChanceOutcomes()`
(`eclipse.cc:1602-1653`) — the action id merely equals the outcome id. That is *better* for
search: MCTS takes a proper expectation, and `mcts.py` already samples `chance_outcomes()`. Only
`initial_setup` hides randomness behind a single fake outcome and consumes the shared `Game` RNG,
which play-time search never re-resolves.

- **Use vanilla MCTS, not IS-MCTS.** `EclipseState` does not override `ResampleFromInfostate`, so
  both IS-MCTS bots throw on a `kImperfectInformation` game. Fine here: no per-player private
  state, and bag *composition* is deducible from public play while the next draw is exactly what
  the explicit chance distributions model. Both `mcts.py` and the C++ `MCTSBot` are N-player and
  general-sum by construction.
- **Do not port anything from `alpha_zero/`.** It was generalized to N-player general-sum with a
  `num_players` value head, but it is JAX/Flax + orbax (not the PyTorch trained net) and was
  **never run on the real Eclipse game** — its tests use `tic_tac_toe` and `colored_trails`, and
  `examples/alpha_zero_eclipse.py` self-describes as a "starting point". The C++/LibTorch
  AlphaZero is hard-asserted 2-player-only (`alpha_zero_torch/alpha_zero.cc:507-508`).
  Instead: write a PyTorch-backed `Evaluator` (prior from the actor, value from the rank critic)
  and hand it to the generic Python `MCTSBot`.
- **UI wiring is easy.** `lobby.game_blob` *is* `EclipseState::Serialize()`'s JSON
  (`eclipse.cc:1657-1664`) and round-trips losslessly through `pyspiel.Game.deserialize_state()`
  to an identical observation tensor. `eclipse_ui_native.so` and `pyspiel.so` build from the same
  sources in the same CMake configuration (`open_spiel/CMakeLists.txt:298-299`).
  1. Fix `apps/eclipse_ui/run.sh:12` — `PYTHONPATH` points at `$REPO_ROOT/build/python`, which
     does not exist; the module is at `$REPO_ROOT/build/open_spiel/python`.
  2. Import `pyspiel` in `api/main.py` (it imports only `eclipse_ui_native` today) and deserialize
     the blob. `api/open_spiel_bridge.py` already has the helpers but is **dead code**.
  3. Replace `random.choice(legal)` in `_autoplay_ai` (`api/main.py:300`) with policy + search.
  4. Rebuild **both** targets after any `eclipse.cc` change — a stale `eclipse_ui_native.so`
     would silently diverge.
- Separate small issue: `broadcast_lobby` (`api/main.py:340-350`) sends the full state to every
  websocket client — an information leak for human-vs-human play in the UI.
